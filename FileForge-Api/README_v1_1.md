# FileForge AI Database v1.1 — React/MSAL/Personal OneDrive update

## Choose ONE SQL script
- **New empty database:** `fileforge_full_schema_v1_1.sql` (full 63-table original foundation plus 2 new tables and additive columns).
- **Existing database already running original v1 SQL:** `fileforge_migration_v1_to_v1_1.sql` (additive migration only). Take a backup first; do not run the full schema again.
- Original `fileforge_full_schema.sql` is retained for comparison only.

## What's new
- `core.user_identities`: Microsoft personal/organizational identities keyed by provider, issuer and subject. Avoid email as an immutable identity key.
- `storage.connections`: owner user, delegated/application mode, connection state, drive ID, FileForge root folder reference, consented scopes, external secret reference.
- `storage.folder_mappings`: workspace-scoped module-to-OneDrive-folder mapping; folder item IDs resolved per connection.
- `storage.files`: external drive, web URL, eTag/cTag, modified timestamp.
- `email.accounts`: owner, delegated authentication mode, connection status.
- Original workspace, roles, contacts, scanning, QR, scraper, document, email, billing, processing, and audit structures preserved.

## Important security and runtime limitations
- Personal OneDrive requires **delegated** Graph access; no app-only background access. A user's personal OneDrive is not a workspace-wide service account. Enforce owner consent and workspace authorization on every operation.
- Graph Explorer success confirms Explorer's own access, **not** FileForge app's MSAL authorization. Verify the registered FileForge client separately.
- MSAL React SPA uses authorization code + PKCE. Browser tokens must never be sent to PostgreSQL; do not use a Graph access token as a NestJS API access token.
- If NestJS must access Graph on behalf of users, design a proper delegated/OBO flow with a separately exposed API and securely managed encrypted token cache. Background jobs may need reauthentication and cannot assume indefinite access.
- `secret_reference` is a pointer only. `config`, `details`, and other JSONB must never contain secrets or access/refresh tokens.
- Do not seed the observed personal drive/folder IDs globally; connect them after workspace/user ownership is established. Do not expose a user's personal OneDrive to other workspace members without explicit authorization.
- `Files.ReadWrite` is enough for current user-owned file operations. Graph Explorer consent is separate from FileForge app consent.
- Email permissions do not guarantee that a personal mailbox supports every enterprise Outlook/Graph capability. Test each mail feature separately.
- This is a schema design update, **not** proof of successful migration execution; validate on staging before production.

## Observed setup (configuration reference only)
- Provider: `onedrive`, type `personal`; root folder `FileForge`.
- Subfolders: `business-cards`, `email-attachments`, `exports`, `invoices`, `pdf-documents`, `qr-scans`, `receipts`, `reports`.
- React + Vite, MSAL React; redirect `http://localhost:3000` (configure Vite port accordingly).

# FileForge AI — Complete PostgreSQL database foundation

**Target:** PostgreSQL 17 (Azure Database for PostgreSQL Flexible Server). **63 tables** in 12 PostgreSQL schemas. This is a first-pass, comprehensive architecture for review and controlled deployment, not a security-certified production schema.

## Scope

| Schema | Purpose |
|---|---|
| `master` | Master lookups for tools, entity types, job statuses, storage providers, contact sources and email events |
| `core` | Users, personal/team workspaces, roles, permissions, memberships, invitations and settings |
| `contact` | Shared contacts, contact methods, addresses, groups, entity links, merges, communication preferences |
| `storage` | Provider connections, file metadata, external file versions, entity associations and storage operations |
| `processing` | Common jobs, job items, events, AI usage and export references |
| `scanner` | Business-card scans, extracted fields and reviews |
| `qr` | QR batches, items and extraction results |
| `scraper` | Public web extraction definitions, runs, pages and records |
| `document` | PDF metadata, extraction templates and versions, extraction runs and fields |
| `email` | Connected email accounts, messages, attachment references, analyses, templates, campaigns, recipients, delivery events and suppressions |
| `billing` | Customers, invoices, line items, payments and receipts |
| `audit` | Append-only audit events and entity snapshots |

## Design guarantees and conventions

- Every table has `id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY`; each table gets its own sequence.
- Ordinary mutable business tables include `created_at`, `created_by`, `updated_at`, `updated_by`, `is_deleted`, `deleted_at`, `deleted_by` and a deletion-consistency check.
- Event/history tables are append-only and intentionally **do not** carry mutable soft-delete/audit columns. Their IDs remain mandatory.
- Every workspace-owned operational table includes `workspace_id` and a foreign key to `core.workspaces`.
- Files are **external only**. `storage.files` holds provider connection, object identifier, path and metadata. Never store file bytes, PDF bodies, base64 files, or authentication tokens in PostgreSQL.
- External provider secrets are referenced by `secret_reference`, not stored as passwords or tokens in this schema. `config` must not be populated with secrets.
- The storage provider master list includes Azure Blob, SharePoint, OneDrive and Cloudflare R2. The storage service must implement authorization, retries and safe deletion outside SQL.
- Contact-to-tool links use an `entity_type_id` + `entity_id` pair. **Polymorphic entity references are not FK-enforced** and must be validated by the application or replaced with dedicated FK link tables.
- Email opt-out/suppression is modeled, but lawful basis, sending compliance, provider rate limits and unsubscribe enforcement require implementation beyond the schema.

## Run

1. Create a new empty database, e.g. `fileforge_db`, in pgAdmin.
2. Open **Query Tool** for that database.
3. Load `fileforge_full_schema.sql` and execute it **once** as a database owner with schema creation privileges.
4. Confirm the transaction commits and verify the schemas/tables in Object Explorer.
5. Do not rerun this file against an existing populated database; use versioned migrations for later changes.

The SQL file uses `BEGIN`/`COMMIT` and `CREATE TABLE` without `IF NOT EXISTS` to surface unexpected existing objects. If an error occurs, roll back and correct the cause rather than repeatedly rerunning partial SQL.

## Production-hardening work before deployment

1. **Workspace isolation:** While workspace IDs and several composite FKs are included, **not every cross-table relation has a same-workspace composite FK**. Add composite `(id, workspace_id)` unique keys and same-workspace FKs systematically, and implement/test PostgreSQL row-level security (RLS) or a rigorously enforced tenant-scoping data access layer. The schema alone does **not** enforce tenant isolation.
2. **Audit:** `created_by`, `updated_by`, and `deleted_by` are columns, not automatic user-attribution. Populate them from trusted identity context; add database-enforced user references and automatic audit capture as needed. Current append-only audit tables must be written to explicitly. `created_by`/`updated_by` do not have FKs in this draft to avoid bootstrapping cycles and allow service actors.
3. **Soft-delete behavior:** Query filters, retention, related child handling, restore rules, and parent/child soft-delete consistency are application responsibilities. `updated_at` is automatically set on UPDATE, but `updated_by` is not.
4. **Storage security:** Protect provider credentials in a secrets manager; store only references. Enforce allowed container/site/drive, expiring download links, file malware scanning and external object retention policies.
5. **AI/scraping privacy:** Scraper rules must respect website permissions and rate limits. AI results and email content may contain sensitive data; apply retention and access policies. `raw_extraction`, `snippet` and other JSON/text fields contain *structured information*, not uploaded file binaries.
6. **Indexes/uniqueness:** Review actual access patterns, normalized email matching, contact duplicate rules, and partial unique indexes. Some foreign keys will need extra indexes at scale.
7. **Business logic:** Monetary totals, email consent validation, statuses, job transitions, identity sequence reset after bulk imports, and invoice immutability after issuance require service/database enforcement.
8. **Migration review:** Test on a staging database, validate backup/restore, and add migrations rather than applying this bootstrap script to production data.

## Implementation order

1. `master` and `core` identity/workspace setup
2. `storage` external provider connections and file metadata
3. `contact` shared contact repository and entity links
4. `processing` jobs and audit logging
5. `scanner`, `qr`, `scraper`, `document`
6. `email` analysis and campaigns
7. `billing` invoice/receipt modules

**Note:** This schema has not been executed against a live PostgreSQL instance in this environment. Run it first on a disposable database and report any SQL errors for correction.
